# DukaanFlow — Backend

FastAPI backend for DukaanFlow (modular monolith, Python 3.13, PostgreSQL).

## Setup

```bash
cd backend
python3.13 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env        # set DATABASE_URL (percent-encode special chars in the password)
```

## Database

```bash
alembic upgrade head                 # create/upgrade all tables
python -m seed.run_seed              # insert demo data (safe to run repeatedly)

alembic current                      # show applied revision
alembic check                        # verify models and migrations are in sync
alembic revision --autogenerate -m "describe change"   # new migration after model changes
alembic downgrade base               # drop everything (dev only)
```

Always review autogenerated migrations before applying them.

`python -m seed.run_seed` loads master data (users, retailers, products, prices, schemes,
stock, credit, aliases) and then demo activity from `seed/demo_activity.py`, created through the
real services in one transaction: orders `DF-DEMO-0001`…`0004` (APPROVED, PENDING AI order with an
Order Desk correction, CREDIT_HOLD, REJECTED), a pending AI extraction with an unclear unit, a
payment and a restock. Both parts are skipped if already present.

### Testing the database

1. Automated: `pytest -v` (schema, constraints, seed, pricing, workflows, access, concurrency).
   `pytest tests/test_concurrency.py -v` runs only the row-locking tests.
2. Inspect the data (`psql -h localhost -U postgres -d <database>`):

```sql
SELECT order_number, status, source, grand_total FROM orders ORDER BY order_number;
-- each of these must return no rows:
SELECT a.retailer_id FROM credit_accounts a LEFT JOIN credit_ledger l USING (retailer_id)
  GROUP BY a.retailer_id, a.current_outstanding HAVING COALESCE(SUM(l.amount),0) <> a.current_outstanding;
SELECT i.product_id FROM inventory i LEFT JOIN stock_movements m USING (product_id)
  GROUP BY i.product_id, i.stock_cases HAVING COALESCE(SUM(m.quantity),0) <> i.stock_cases;
```

3. Constraints reject bad data. Run each statement on its own; each one fails, so nothing changes:

```sql
UPDATE inventory SET stock_cases = -1;                                         -- ck_inventory_stock_non_negative
INSERT INTO users (name, phone, role) VALUES ('x', '9111111111', 'SUPERVISOR'); -- ck_users_role_valid
INSERT INTO products (sku, name, brand, category_id, pack_size, units_per_case, base_unit, order_unit, gst_rate)
  SELECT 'SKU-BS-075', 'dup', 'x', category_id, '1', 1, 'piece', 'case', 5 FROM products LIMIT 1;  -- uq_products_sku
```

4. Watch a row lock by hand with two psql sessions:

```sql
-- session A
BEGIN;
SELECT * FROM inventory WHERE product_id = (SELECT id FROM products WHERE sku = 'SKU-DW-500') FOR UPDATE;
-- session B: blocks until A finishes
UPDATE inventory SET stock_cases = stock_cases - 1
 WHERE product_id = (SELECT id FROM products WHERE sku = 'SKU-DW-500');
-- session A
ROLLBACK;   -- session B continues immediately
```

## Run

```bash
uvicorn app.main:app --reload --port 8000
```

- Health check: http://localhost:8000/api/v1/health
- OpenAPI docs: http://localhost:8000/docs

### Authentication

| Endpoint | Purpose |
|---|---|
| `POST /api/v1/auth/send-otp` | `{"phone"}`: emails an OTP to an active retailer's registered address (valid 120 s); same response for every number |
| `POST /api/v1/auth/verify-otp` | `{"phone", "otp"}` → access token + user (5 attempts per OTP) |
| `POST /api/v1/auth/login` | `{"phone", "password"}` → access token + user (salesman, order desk, admin) |
| `GET /api/v1/auth/me` | Current user (`Authorization: Bearer <token>`) |

- Both login methods need Upstash Redis (`UPSTASH_REDIS_REST_URL`, `UPSTASH_REDIS_REST_TOKEN`) for OTPs
  and rate limits; without it they return 503 `AUTH_SERVICE_UNAVAILABLE`.
- Limits per phone number: resend cooldown 60 s, 5 OTP requests per 15 min, 5 password attempts per 15 min.
- Email: `EMAIL_PROVIDER=mock` (development only) prints the OTP in the backend console as
  `WARNING  dukaanflow.email: [DEV MOCK EMAIL] OTP for … is …`. `EMAIL_PROVIDER=brevo` sends a real
  email to the retailer's `users.email` and needs `BREVO_API_KEY` and `BREVO_SENDER_EMAIL` (a sender
  verified in Brevo). A retailer without an email gets 503 `OTP_DELIVERY_FAILED`. Production must use
  `brevo`. Restart the server after changing `.env`.
- Demo retailers: 9000000101 (Sharma), 9000000102 (Gupta). Internal demo users get a password from
  `DEMO_STAFF_PASSWORD` when you run `python -m seed.run_seed`.

### Ordering (Milestone 2)

| Endpoint | Who | Purpose |
|---|---|---|
| `GET /api/v1/products`, `/products/categories` | retailer (own), staff with `retailer_id` | Catalogue with the retailer's prices, stock, active schemes |
| `POST /api/v1/orders/quote` | retailer, salesman | Price a cart (schemes, GST, totals, stock) without ordering |
| `POST /api/v1/orders` | retailer, salesman | Place an order (backend prices everything) |
| `GET /api/v1/orders`, `/orders/{id}` | own / assigned / all | History, desk queue (`status`, `source`, `search`, paging) |
| `PATCH /orders/{id}/items/{item_id}`, `POST /orders/{id}/hold`, `/approve`, `/reject` | order desk, admin | Review, correct, hold, confirm, reject |
| `GET /api/v1/order-desk/summary` | order desk, admin | Counts per status |
| `POST /api/v1/ai-orders/extract`, `/ai-orders/{id}/confirm` | retailer, salesman | Message → draft → order (source AI) |
| `GET /api/v1/exports/tally/orders.csv` | order desk, admin | Confirmed orders as Tally CSV |

- AI order capture needs `OPENAI_API_KEY` in `backend/.env` (optional `OPENAI_MODEL`, default
  `gpt-4o-mini`; `OPENAI_BASE_URL` for an OpenAI-compatible endpoint). Without a key the extract endpoint
  returns 503 `AI_NOT_CONFIGURED`; everything else works.
- Product images: set `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET` in
  `backend/.env`, then (as ADMIN) `curl -H "Authorization: Bearer <token>" -F "file=@biscuit.png"
  http://localhost:8000/api/v1/products/<product_id>/image`. Without Cloudinary, products show pack
  illustrations; the frontend switches to the uploaded photos automatically.
- Order desk login needs a staff password: set `DEMO_STAFF_PASSWORD` in `.env` and run
  `python -m seed.run_seed` (order desk: 9000000002, admin: 9000000001).

### Development-only endpoints

Mounted only when `ENVIRONMENT=development`; they have no authentication.

| Endpoint | Purpose |
|---|---|
| `GET /api/v1/dev/db-status` | Runs a query; returns database, server version, migration revision |
| `GET /api/v1/dev/seed-summary` | Row counts for all 17 tables, users by role, orders by status |
| `GET /api/v1/dev/products` | Products with category and stock |
| `GET /api/v1/dev/retailers` | Retailers with assigned salesman and credit |
| `GET /api/v1/dev/retailers/{retailer_id}/products` | Products with that retailer's current price and active schemes |
| `GET /api/v1/dev/retailers/{retailer_id}/credit` | Credit limit, outstanding, available credit and every ledger entry |
| `GET /api/v1/dev/users` | All users with role and linked retailer |
| `GET /api/v1/dev/orders?status=` | Orders with retailer, source, status and totals (optional status filter) |
| `GET /api/v1/dev/orders/{id or number}` | One order (e.g. `DF-DEMO-0002`): item snapshots, corrections, stock movements, ledger entries |
| `GET /api/v1/dev/ai-extractions` | AI extractions with their items and the order they became (if confirmed) |
| `GET /api/v1/dev/inventory` | Stock per product with its movement history |
| `GET /api/v1/dev/integrity` | Runs 9 consistency checks (ledger = outstanding, movements = stock, totals = items, …) |

## Test

```bash
pytest                                   # all tests
pytest tests/test_dev_api.py             # one file
pytest tests/test_health.py::test_health_returns_standard_success_response   # one test
```

Database tests use a separate test database (`TEST_DATABASE_URL`, default `<database>_test`).
The suite creates it if needed, rebuilds it with Alembic and seeds it on every run.
They are skipped if PostgreSQL is unreachable.

## Layout

```text
app/
├── main.py         # create_app(): CORS, exception handlers, /api/v1 router (+ dev router)
├── core/           # settings, enums/error codes, shared deps, permissions.py (role + retailer access)
├── database/       # engine + pool (connection.py), Base (base.py), sessions (session.py)
├── models/         # SQLAlchemy models, one file per domain; __init__ registers all
├── schemas/        # shared Pydantic schemas (ApiResponse envelope)
├── modules/        # business modules: router → controller → service → repository
│   ├── pricing/    # price selection + scheme/GST calculation
│   ├── orders/     # order creation, Order Desk corrections, approval, rejection
│   ├── ai_orders/  # AI extraction records and their human confirmation
│   ├── inventory/  # stock reads and row locks
│   ├── retailers/  # retailer access and credit
│   └── dev/        # temporary development-only verification endpoints
├── exceptions/     # AppException + centralized handlers
└── utils/          # response envelope helpers, text normalization
migrations/         # Alembic environment and versions
seed/               # demo_data.py (data + assumptions), run_seed.py (idempotent loader)
tests/
```

All responses use the standard envelope from `docs/API_DESIGN.MD`:
success → `{success, message, data}`, error → `{success, message, error_code, details}`.
Raise `app.exceptions.base.AppException` for expected errors. Database connection
failures return HTTP 503 with `DATABASE_UNAVAILABLE`.
